# Architecture and API contracts

## Components

- `public/index.html`, `public/styles.css`: browser UI; accessible input and SVG heart diagram.
- `public/app.js`: frontend state, messages, lesson selection, fetch requests, and diagram interaction. No credentials embedded.
- `src/server.js`: Node.js core HTTP server, allowlisted static assets, session cookies, optional reviewer access code, origin checks, basic request throttling, error handling.
- `src/lessons.js`: four learning objectives, opening questions, practice content, and educational references.
- `src/engine.js`: application-level Socratic question engine and counter, turn bounds, tutor instructions, response validation, practice flow.
- `src/provider.js`: OpenAI Responses API request and text extraction; non-persistent (`store:false`).

## Request lifecycle

1. `GET /api/lessons` returns lesson titles and first questions; `GET /api/health` returns service health and a boolean for AI configuration.
2. `POST /api/session` with `{ "lessonId":"algebra", "mode":"practice" }` creates a new server-side conversation for the visitor; `mode` can be `practice` or `live`.
3. `POST /api/message` with `{ "action":"answer", "answer":"subtract 3" }` sends a student answer. For `hint` or `breakdown`, `answer` can be omitted and the turn does not advance.
4. The engine selects a practice step or calls the Responses API with the last 16 history entries and lesson-specific instructions. An output JSON object containing `reply` (text) and `done` (boolean) is validated, then returned.
5. The backend assigns an initial lesson-specific target of three to five answers and can adjust the target to three through six when a live model suggests it. Instructional prompts can request earlier completion if understanding is demonstrated. Since the app has no autonomous mastery assessment, the feedback should not be treated as a verified learning outcome.

Success: `{ "reply":"...", "done":false, "turn":1, "target":4 }`. Errors: `{ "error":"..." }` and HTTP status codes. Non-success responses are never silently interpreted as successful tutoring.

## Security and data handling

API key resides only in server environment. Configured `APP_ORIGIN` must match browser `Origin` on POST requests. HttpOnly, SameSite=Strict cookies store an opaque random ID; sessions and turn histories live in process memory. Reviewer access tokens (when configured) are validated server-side. Basic rate limiting allows up to 40 API POST requests per minute per visitor; an unbounded public site would need shared throttling, authentication, abuse detection, observability, and session storage. Cookies have a two-hour max age. No database is used. `store:false` requests non-persistence of Responses on the provider side; consult provider privacy terms for other data handling.

## Limitations

- Four predefined lesson goals; custom subjects and uploads are not implemented.
- Guided-practice feedback is scripted and illustrative; live feedback is generated by OpenAI.
- The first question is curated, not produced by a separate decomposition call. In live mode, the AI uses lesson objectives and prior answers to form subsequent questions. If automatic upfront question decomposition is desired, add a separate planning step with a validated plan object.
- Single process only, no durable storage or automatic retries after network outages.
- Remote responses may be inaccurate; human review is essential in high-stakes instructional uses.
